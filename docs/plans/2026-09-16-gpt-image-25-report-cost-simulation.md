# 危険報告の画像生成を GPT Image 2.5 に移行した場合のコスト試算

作成日: 2026-09-16
再現: `npx tsx scripts/simulate-gpt-image-25-cost.ts`

## 結論(先に)

- **medium 品質で置き換えると、画像生成コストは現行の約 2.2 倍**になる。
  報告 1,000件/月で **$193 → $420(+$227/月)**。
- **low 品質なら現行より約 2割安い**($193 → $150/月)。ただし low は
  ドラフト向け画質で、報告書に載せる画像としては要検証。
- **high 品質は約 6.9 倍**($193 → $1,328/月)。品質要件が明確でない限り推奨しない。
- 最大の不確実性は **GPT Image 2.5 の tier 別出力トークン数が未公表**である点。
  下の感度分析(§4)でレンジを押さえてあるが、**実測 1 回でほぼ確定する**ので
  移行判断の前に §6 のキャリブレーションを実施すべき。

## 1. 現状の構造(コードから)

| 項目 | 実装 | 参照 |
| --- | --- | --- |
| 本線モデル | `gemini-3.1-flash-lite-image`(Nano Banana 2 Lite) | `lib/gemini-image.ts:19` |
| 実効単価 | $0.0336 / 枚 | `lib/api-cost-calculator.ts` |
| OpenAI 経路 | `textInImage=true`(日本語文字入り素材)のときのみ `gpt-image-2` | `app/api/gemini/generate-image/route.ts:253-` |
| 画像サイズ / 品質 | `1024x1024` / `medium` | `lib/openai-image.ts:40,95` |
| 生成方式 | 元写真ありの image-to-image(`images.edit`) | `lib/openai-image.ts:145-` |

報告 1 件あたりの生成回数(`components/danger-report/danger-report-form.tsx` の自動生成フロー):

- viz(可視化): 1 枚
- 災害シミュレーション: 地震・台風・火災 + 浸水(浸水区域内のみ) = 3〜4 枚
- 機械検証による是正再生成: 最大 1 回(`lib/disaster-image-verification.ts`)

→ 基準ケース **5 枚 × 是正再生成 15% = 5.75 枚/報告**。

## 2. GPT Image 2.5 の料金(公表値)

sunburst / flare 共通:

| 区分 | 単価 |
| --- | --- |
| 画像入力 | $8 / 1M tok |
| 画像入力(キャッシュ) | $2 / 1M tok |
| テキスト入力 | $5 / 1M tok |
| テキスト入力(キャッシュ) | $1.25 / 1M tok |
| 画像出力 | $30 / 1M tok |

品質 tier は `low / medium / high / xhigh / max`(2.5 で `xhigh` `max` が新設)。

**注意**: 出力単価は `gpt-image-2` と同じ $30/1M だが、OpenAI ドキュメントは
「同じ tier でもモデルによってトークン消費量は異なりうる」と明記しており、
2.5 の tier 別トークン数は対話型カリキュレータでしか提供されていない。
本試算では **`gpt-image-2` の公表 per-image 価格から逆算したトークン数を代理値**
として使用している(low 200 / medium 1,767 / high 7,033 tok @1024x1024)。
`xhigh` `max` は代理値すら無いため「要実測」とした。

## 5. 見落としやすい論点

1. **枚数が倍になるリスク**: 現行 Gemini 経路は 1 リクエストで最大 2 枚返し、
   UI も 2 枚採用する(`danger-report-form.tsx` の `imgs.slice(0, 2)`)。
   GPT Image は `n=1`。同じ枚数を出すならリクエスト数が倍 → **月次コストも倍**。
   移行時に「1 枚に減らす」プロダクト判断をセットで行う必要がある。
2. **キャッシュ入力が効く構造**: 1 報告で同じ参照写真に対し 5 枚生成するため、
   2 枚目以降が画像入力キャッシュ($8→$2/M)に乗れば入力コストは約 1/4。
   low 運用では総額の差が大きい。
3. **是正再生成は現状 OpenAI 経路で動いていない**。
   `verifyOrRegenerateImages` は Gemini 経路のみ。移行時に有効化するなら
   `--regen` を上げて再試算すること(再生成率 100% なら単純に 2 倍)。
4. **一括生成(24プロンプト)**: 1 回あたり現行 $0.81 → 2.5 medium $1.75 / high $5.54。
   管理者機能なので頻度は低いが、high 運用時は無視できない。

## 6. 実測によるキャリブレーション(移行判断の前に)

1. `OPENAI_IMAGE_MODEL=gpt-image-2.5-flare` で報告フローを 1 回流す
2. `lib/openai-image.ts` の `toImageGenerationUsage` が拾う `response.usage`
   (`input_tokens` / `input_tokens_details.image_tokens` / `output_tokens`)を記録
3. `npx tsx scripts/simulate-gpt-image-25-cost.ts --img-in=<実測> --txt-in=<実測>` で再実行
4. 確定後、`lib/api-cost-calculator.ts` に `gpt-image-2.5-*` の単価定義を追加
   (現状 `gpt-image-2` / `gpt-image-1` のみ。2.5 は fallback $0.04 に落ちる)

## 7. 推奨

- **まず flare の low / medium を実測**し、画質が報告書用途に耐えるか目視で判断する。
- コスト増を許容できるなら **medium 置き換え(+$227/月 @1,000件)** が妥当線。
- **移行するなら「1リクエスト1枚」への整理を同時に行う**(論点 5-1)。
  ここを放置すると試算の倍のコストになる。
- `xhigh` / `max` は公表データが無く、high(6.9x)以上であることだけが確か。
  現時点で採用判断はできない。
