## 1. 作業の境界と実装順

最初に費用を発生させる生成経路を停止する。その後、既存データで効果を確かめやすい印刷UIと用紙を改善し、写真クイズの学習一巡を通す。最後に作成・共有・結果から印刷への接続を仕上げる。

  ↓
T02 World Labs生成停止とデータ互換
  ↓
T03 印刷用データ・用途別情報の分離
  ↓
T04 A4ページ構成 → T05 印刷UI → T06 PDF・印刷出力
  ↓ チェックポイントA：既存チェックシートの改善を実物で確認

  ↓

  ↓ チェックポイントB：確認用3地点を各端末で完走

各作業は「失敗を確認できる検証→最小の実装→その作業の確認」を基本とする。寸法・色等の可逆な調整に、実装をなぞるだけの単体テストを増やさない。画面・紙面はブラウザと実出力で確認する。

作業は現在のタスクで順次進められる構成。作業前から存在する変更・未追跡ファイルを削除したり戻したりしない。コミットや公開作業のために無関係な変更をまとめない。

## 2. 先に決めるデータと動作

### 2.1 コースと問題

既存のD1コースのJSONに `learningMode: 'photo-quiz-v1' | 'legacy-3d'` を加える。フィールドのない既存コースは `legacy-3d` として読み取る。既存の3D状態を一律にreadyへ変更しない。

写真クイズには、次の確認済み問題設定を保存する。

```ts
// 計画用の契約例。実装時はZodと既存ID形式に合わせる。
type PhotoQuizItem = {
  id: string
  sceneId: string
  photoIndex: number
  templateId: string
  templateVersion: number
  scenario: 'normal' | 'rain' | 'evening' | 'earthquake'
  evidence: { observed: string; hypothetical: string }
  region: { x: number; y: number; width: number; height: number }
  // 場所を選ぶ代替操作用。確認済みの中立的な候補。
  locationOptions: Array<{ id: string; label: string; region: Rect }>
}
```

`Rect` は同じ正規化矩形型。矩形の座標・幅・高さ、境界内、重なり、写真の存在、分類とテンプレートの一致、文字数をサーバーで検証する。自由な正解文字列をリクエストから受け取らない。座標はマスク・回転処理後の画像に対するものとする。

写真クイズの準備状態は、保存済み写真と有効な通常問題がそろった時点でreadyにできる。`reviewCourse`・`publishCourse`は新モードの検証を使い、SPZの存在を要求しない。作成者のプレビュー確認と公開操作を必要とし、以前の合意どおり教員の承認は必須にしない。

1回の学習は最大3地点、基本は1地点1主題。教材は「起こりそうなことと理由」「安全な行動」の2問を持つ。高学年の発展問題を追加する場合は、基本コースの完了条件に混ぜない。

学習用の取得データと、編集用の取得データを分ける。学習者向け一覧・コース詳細・セッションAPIに、正解領域、正解ID、未回答の解説、R2キー、元の位置情報を含めない。回答後にその問いの説明・図示だけを返す。

### 2.2 学習セッション

新しいD1テーブルを追加し、既存の3D進捗テーブルを破壊的に変更しない。

| テーブル案 | 主な用途・制約 |
|---|---|
| `hunter_photo_quiz_sessions` | 利用者、コース、コース版、シナリオ、学年、固定した問題ID、教材版、状態、作成・更新日時、行のversion |
| `hunter_photo_quiz_events` | セッション、回答requestId、問題ID、段階、判定、ヒント使用、作成日時。`(session_id, request_id)`に一意制約 |

セッションには現在の段階・初回回答・最終正答・選択肢の順序を保持する。開始時に教材の必要なスナップショットをサーバー用JSONへ保存し、教材更新で途中の問題の意味が変わらないようにする。イベントとセッション更新は、D1で実行可能なトランザクション／条件付きbatchを実機のローカルDBで確認して実装する。

- 同じ回答の再送は同じ結果を返し、回数を加算しない。
- 次の問いを先に送る、不正なID、別利用者のセッション、解除された共有は拒否する。
- 途中の通信断は入力を保持し、同じrequestIdで再送する。ネットワークが戻るまでは未保存表示を維持する。
- コースの内容変更・共有解除後は古い版を完了扱いにしない。既存の途中記録は履歴として残し、新しい版の開始を案内する。
- 2問の理解確認が完了した地点だけをクリアにする。ヒントを使って学べたことと、自力で初回正答したことは区別する。
- 自宅の画像や位置情報、児童名をローカルストレージ・分析ログへ保存しない。写真は既存の認証付き配信を使う。

### 2.3 印刷用の共通契約

```ts
type PrintPurpose = 'family' | 'school'
type PrintDocument = {
  purpose: PrintPurpose
  title: string
  generatedAt: string
  reviewedAt?: string
  gradeBand: 'lower' | 'middle' | 'upper' | 'junior'
  map?: { sharedGeometry: unknown; markers: PrintMarker[] }
  items: PrintItem[] // 表示順、連番、場所、確認事項、行動、許可された写真
  pages: PrintPage[] // A4内の配置・続き・ページ番号を確定した結果
}
```

契約例の`unknown`は実装で既存GeoJSON型に置き換える。画像は所有・共有を確認したアプリ内の参照だけを受け付け、任意のURLをサーバーに取得させる機能を追加しない。

`purpose === 'school'` では、許可するフィールドだけから新しいオブジェクトを作る。家庭用文書から写真だけ非表示にする実装は禁止。学校用は「学校東側コース」等の共有名、確認済みの短い説明、公開してよい区間だけを用いる。共有名・区間が未設定なら、一般名や地図なしで準備できる。

既存`UserRoute + DangerReport[]`と写真クイズコースを別々のadapterで変換する。危険投稿の全件を新しいクイズ問題へ自動変換する処理は追加しない。

### 2.4 出力方式の決定

1. 用途・選択地点を確定し、許可されたデータだけを文書に含める。
2. 画像とフォントを読み込み、A4の内容領域186×273mmで項目を計測する。
3. 分割可能な単位ごとにページへ配置する。用紙の高さを超える単一項目は、見出し付きの「つづき」に分ける。
4. 同じページDOMをプレビュー、印刷用のDOM、PDFの描画元に使う。
5. PDFダウンロードは既存jsPDFを維持し、各A4ページを1枚ずつ描画。作成したcanvasは順次解放する。

ブラウザ印刷ではテキストを保持するが、PDFダウンロードは画像ベースのためテキスト検索や読み上げ対応を保証しない。プレビューの「内容を読む」はHTMLで提供する。後から別のPDFエンジンを導入することを初期版の前提にしない。

## 6. 注意する判断と残る確認

- 実物の印刷と子どもの利用テストは、開発環境のスクリーンショットだけで完了扱いにしない。
- 「3分」は設計上の目安。理解に時間をかける利用者を失敗扱いにしない。
- 表札・ナンバーの完全自動検出は別途の精度・速度評価が必要。現行の自動顔検出＋手動補正を使う初期版の範囲を明示する。
- 既存の周辺危険一覧は公開投稿を最大2000件取得して絞り込む実装。表示対象を全ての危険の網羅と表現しない。今回のUIには選択と確認日を示し、検索API全体の再設計は独立した課題として扱う。
- Mapboxの既存静的地図はマーカー数等の制限を持つ。多数地点は複数の用紙・地図に分け、近接マーカーをずらす場合は引き出し線などで本来の位置を分かるようにする。
- 本番公開、リモートDBへのmigration、外部サービスの契約は、完成した変更・検証結果を確認できる段階で別途扱う。ローカルの設計・実装・検証を進めるための承認待ちにはしない。
