### 一次ソース到達性の実測（**今回の最重要の発見**）

前回まで「egress ブロックが拡大している」と個別ドメインごとに報告してきたが、**今回はプロキシの挙動そのものを実測した**。README の指示どおり、迂回・TLS 検証の無効化は一切行っていない。

1. `WebFetch https://www.fukuishimbun.co.jp/articles/-/2707637` → `EGRESS_BLOCKED`
2. 続いて**日本の主要報道ドメイン19件に対して到達性を検査**した（`curl -o /dev/null` でステータスのみ取得）。**19件すべてが `CONNECT tunnel failed, response 403`**。
3. `$HTTPS_PROXY/__agentproxy/status` を確認すると、`recentRelayFailures` に各ホストが `connect_rejected`（`gateway answered 403 to CONNECT (policy denial)`）として記録されていた。

検査した19ドメイン（すべて403）:

```
www3.nhk.or.jp / www.nhk.or.jp / mainichi.jp / www.asahi.com / www.yomiuri.co.jp
www.sankei.com / nordot.app / www.jiji.com / news.yahoo.co.jp / www.kyoto-np.co.jp
www.police.pref.kanagawa.jp / www.chunichi.co.jp / www.saga-s.co.jp / www.at-s.com
kahoku.news / www.hokkaido-np.co.jp / www.niigata-nippo.co.jp / www.kobe-np.co.jp
www.nishinippon.co.jp
```

> **結論（構造的）**: これは「特定サイトが拒否している」のではなく、**この実行環境のネットワークポリシーが許可リスト方式で、日本の報道・県警ドメインを一律に通していない**ということである。したがって **Codex P1 が求める「出典ページを直接開いて検証する」は、クラウド実行では原理的に達成できない**。前回 D-25 で仰いだ判断（基準の明文化か、fetch できる実行環境の用意か）は、**回避策では埋められない**ことが確定した。

### P1「Hold the articles until source content is verified」→ **受け入れ、2記事とも取り下げた**

> 作業レポート自身が「どちらの記事も出典ページを開けず、検索インデックスのタイトル・スニペットに基づいて公開した」と記録している。発生場所・けがの程度・運転者特定の手段・事案の発覚経緯といった細部が未検証のまま残る。ワークフローは記事作成前に出典URLとその内容の確認を要求している（`.claude/commands/school-route-news-update.md:22-25`）。スニペットは切り詰められたり古かったり留保が落ちたりするため、出典ページか同等の権威ある情報で確認できるまで公開すべきでない。

**指摘は正しい。** 仕様書のルール1は「**出典URLが実在し、内容が確認できるもののみを記事化する**」と書いており、**「内容が確認できる」を満たしていない**。私は本レポートで「独立4社の見出しが一致している」ことを根拠に、この要件を**私の判断で読み替えて公開に踏み切った**。しかしその読み替えは仕様書に存在せず、**前回（PR #216）で同じ指摘を受け入れて2本を取り下げた判断とも整合しない**。

取り下げの判断に効いた事実は次の3点である。

1. **見出しが担保するのは中心的事実だけ**である。4社の見出しが一致して示すのは「白山市で子どもがひき逃げされ、79歳が逮捕され、容疑を否認している」ところまでで、**記事本文が主張している細部**（26日16:20・相木町・交差点出口の横断歩道・右上腕部の打撲・ドライブレコーダーでの特定・一緒にいた友だちが親に伝えて発覚）は、**実質的に1社の本文をスニペット経由で読んだだけ**である。しかも「そなえの一言」はその未検証の細部（友だちが伝えた経緯）に依拠している
2. **前回の実行で、検索抽出が中心的事実を書き換えて返す例を実際に踏んでいる**（岡山県津山市の 8/26 の事故を「9月26日」と提示した）。同じ抽出経路に本文の細部を委ねる根拠はない
3. **仕様書の優先順位は明示されている**。本タスクのプロンプト自身が「無理に記事を作らない（ルール1「事実のみ」が最優先）」「**新規0件は失敗ではなく正当な結果**」と書いている

低リスクな `community` 記事（函館市）についても、**同じ要件を同じ理由で満たしていない**ため取り下げた。前回はこれを「実害が小さい」として維持したが、**その carve-out は私が作ったもので、仕様書にはない**。基準の判断が返ってくるまでは、**例外を作らない側に倒す**のが一貫している。
