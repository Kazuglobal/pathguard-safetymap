# ユーザー成長ギャップ分析（既存機能の改善 + 追加機能の提案）

- 実施日: 2026-07-25
- ブランチ: `agent/prevent-unverified-safe-house-sign`(`683ea0706`)
- 対象: PathGuardian 全体（地図 / 危険箇所レポート / 通学路 / 通知 / きけんハンター）
- 手法: リポジトリのコード・マイグレーション・設計書の読み取りのみ。**DBの実データ集計・実機検証は未実施**
- 問い: 「もっとあれば役立つ機能」「既存機能のどこを改善すればユーザーが増えるか」

## 0. 結論

**新機能を足す前に、既存機能の「入口が塞がっている」箇所を開けるほうがユーザー増に直結する。**

特に、Web Push の実装一式（Service Worker・購読テーブル・cron配信）を作り込んでありながら **PWAマニフェストが存在しない**ため、その投資の相当部分が現状ユーザーに届いていない可能性が高い。同様に、地図がログイン必須・レポートが全件手動承認という2点が、それぞれ「登録前に価値を体験できない」「投稿してもフィードバックが返らない」という形で成長を止めている。

以下、A章＝既存機能の穴（すべてコード上で確認）、B章＝未実装の追加機能、C章＝推奨順序。

---

## A. いま成長を止めている穴（コードで確認済み）

### A-1. 地図(`/map`)がログイン必須 — 価値を体験する前に会員登録の壁 🔴

**確認箇所**: `middleware.ts:6-21` の `PROTECTED_PREFIXES` に `/map` が含まれ、未認証アクセスは `/login` へリダイレクトされる（`middleware.ts:70-75`）。

**問題**: このアプリの中心的価値は「うちの子の通学路に危険はあるか」を地図で確認できることだが、それを**確認する前に会員登録が必要**。`/lp`（製品紹介LP、`app/page.tsx` からリダイレクト）で興味を持った訪問者が、価値の実物を見る前に登録フォームに突き当たる構造になっている。

**改善案**: 住所または学校名から周辺の危険ピンを**ログインなしで閲覧できる公開ビュー**を用意し、ログイン要求は「投稿する / 通学路を登録する / 通知を受け取る / 反応する」に限定する。既に `/landing`（ニュースフィード）と `/safety-quest`（きけんハンター）は保護対象外なので、地図だけが取り残されている状態。

**注意点**: 公開ビューでは危険報告の画像を出さない、または署名URL経由に限定するなど、`lib/danger-report-image-access.ts` の非公開バケット方針を崩さないこと。位置精度の粗化（グリッド丸め）も検討対象。

---

### A-2. PWAマニフェストが存在しない — Push通知基盤が半分機能していない 🔴

**確認箇所**:
- `public/` 配下に `manifest.json` / `*.webmanifest` が**存在しない**
- `app/` 配下・`next.config.mjs`・`middleware.ts` のいずれにも `manifest` の文字列が**1件もヒットしない**（grep 0件）
- 一方で Push 実装は揃っている: `public/sw.js`(push/notificationclick ハンドラ)、`supabase/migrations/20260321000000_add_push_subscriptions.sql`、`app/api/push/subscribe|unsubscribe|notify-danger-report|notify-content/`、`app/api/cron/push-danger-reports/route.ts`(15分毎)、`hooks/use-push-subscription.ts`

**問題**: iOS Safari の Web Push は「ホーム画面に追加されたPWA」でのみ動作するというプラットフォーム制約がある（※これはコードではなくプラットフォーム仕様に基づく指摘。実機での確認が必要）。マニフェストが無い＝ホーム画面追加でスタンドアロン起動にならないため、**iPhone ユーザーには通知が届いていない可能性が高い**。日本の保護者層におけるiOS比率を考えると、通知機能の過半が空振りしている恐れがある。

またマニフェスト不在は、Androidを含む全ユーザーで「ホーム画面にアイコンを置いて毎日開く」という再訪導線そのものを塞いでいる。デイリーハビット設計（`school-route-news` v3）とも噛み合わない。

**改善案**:
1. `app/manifest.ts`（Next.js App Router のマニフェスト生成）を追加。`display: "standalone"`、`start_url`、アイコン（192/512、maskable）、`theme_color: "#0ea5e9"`（`app/layout.tsx:30` の既存値と揃える）
2. アイコン実体の作成（現状 `public/apple-touch-icon.png` のみ）
3. iOS向けの「ホーム画面に追加」案内UI（初回訪問時・通知許可を求める前）
4. **実機（iOS/Android）で通知が実際に届くことを検証**してから完了とする

**工数対効果**: 本分析の中で最も低コスト・高効果。

### A-3. 危険箇所レポートが全件手動承認 — 投稿しても地図に出ない 🔴

**確認箇所**:
- `supabase/migrations/20260704090000_restrict_danger_reports_insert_status.sql` — 非adminは `status='pending'` でしかINSERTできないようRLSで拘束
- `lib/danger-report-status.ts:3` — 公開されるのは `["approved", "published", "resolved"]` のみ
- `hooks/use-danger-reports.ts:133` — 地図/一覧は `PUBLIC_DANGER_REPORT_STATUSES` で絞り込み
- 承認は `lib/admin-reports-service.ts:62` の `.update({ status })` のみ、UIは `app/admin/reports/page.tsx`

**問題**: 投稿→公開のあいだに人間の承認が必ず挟まるため、**投稿した本人ですら自分の投稿がすぐ地図に反映されない**。UGC型サービスで投稿のフィードバックループが切れていると投稿数が伸びず、承認スループット（＝管理者の可処分時間）が利用者数の上限を作る。

**改善案**: `docs/plans/2026-07-18-danger-report-ai-moderation-design.md` に AI一次審査による三段階振り分け（自動承認 / 自動保留 / エスカレーション）が**設計済み・実装未着手**として存在する。これを実装するのが最短。設計書の安全原則はそのまま踏襲すること:

1. AI判定は「厳しくする方向」にのみ作用（ヒューリスティックが下限）
2. 画像付き投稿は自動公開しない（初期フェーズ）
3. AI失敗・タイムアウト時は絶対に自動承認しない
4. 自動却下は出さない（却下は必ず人間）

先行実装として不審者アラートのAI一次審査（`lib/suspicious-alert-moderation.ts` / `lib/suspicious-alert-moderation-ai.ts`）があり、二層構造をそのまま汎用化できる。

**補足**: 自動承認が入っても「承認されたら投稿者に通知する」導線がないと本人には見えない。`app/api/push/notify-danger-report` は周辺ユーザー向けなので、投稿者への承認通知は別途必要。

### A-4. ふりがなが「きけんハンター」の中だけ 🟡

**確認箇所**: `lib/hunter/furigana.ts` と `components/safety-quest/hunter/ruby-text.tsx` は hunter 配下限定。地図・レポート・ミッション・バッジ・通学路の各画面には ruby/振り仮名の実装が無い。

**問題**: 「子ども自身が危険を見つけて学ぶ」がコンセプトの中心（`docs/PRODUCT_OVERVIEW.md`）だが、**低学年は本体アプリのテキストを読めない**。子どもが使える画面が hunter だけに限られている＝子ども経由の利用時間・家庭内での定着が伸びない。

**改善案**: `ruby-text.tsx` と furigana 辞書は既存資産なので、hunter 配下から `components/ui/` または `lib/` へ昇格させ、子ども向け画面（危険報告の詳細、ミッション、バッジ、ルートクイズ）へ横展開する。全画面一律ではなく「子どもモード」トグルで切り替える設計のほうが保護者向けUIを壊さない（2026-07-04の親向けUI刷新の方針と両立させること）。

### A-5. 危険情報の鮮度を保つ仕組みがない 🟡

**確認箇所**:
- `resolved` ステータスは型（`lib/admin-reports-service.ts:58`）と管理画面（`app/admin/reports/page.tsx:200`）には存在するが、**ユーザーが状態を報告する導線が無い**
- ユーザーの反応は `danger_report_reactions` の `helpful` / `caution` のみ（`supabase/migrations/20260309235500_add_landing_report_reactions.sql:7`）
- `report_flags`（`20260704090200_add_report_flags.sql`）は不適切投稿の通報専用で、公開状態を変更しない設計

**問題**: ハザードマップは放置すると古い情報が滞留し、「工事はもう終わっている」「その看板はもう無い」といった実態との乖離で信頼を失う。現状、鮮度を回復させる手段が管理者の手動操作しかない。

**改善案**: 詳細画面に「まだあります / 直りました」の1タップ確認を追加し、最終確認日を表示する。一定数の「直りました」が集まったら管理者キューに上げる（自動で `resolved` にはしない＝A-3の安全原則と同じく、状態変更は人間の判断を残す）。これは投稿より心理的ハードルが低く、**投稿しないユーザーでも貢献できる参加口**になる点でも価値がある。

## B. 追加すると効く新機能（未実装）

### B-1. 学校・クラス単位のグループと招待リンク 🔴 バイラルループがゼロ

**確認箇所**:
- `supabase/migrations/` 配下に `school_id` / `class_id` / `group_id` / `organization` を含むテーブル定義が**1件も無い**
- `app/` `components/` `lib/` に `invite` / `招待` の実装が**1件も無い**（grep 0件）

**問題**: 「地域参加型プラットフォーム」を標榜しているが、**同じ学校の保護者どうしが繋がる手段がアプリ内に存在しない**。結果として、1人のユーザーが別のユーザーを連れてくる自然な経路（＝バイラル係数を生む経路）が皆無で、獲得は全て外部流入に依存している。

**改善案**: 学校（またはグループ）エンティティと招待リンクを導入し、
- グループ内で危険箇所と通学路を共有
- 「同じ学校の保護者が3人参加しています」のような可視化
- PTA・学年連絡網での拡散を想定した共有文面

既存の学校サマリーPDF出力（`lib/report-generation/`、写真・description を含めない教育版設計）と噛み合い、「PTAに持っていく資料が出せる」という導入理由にもなる。

**留意**: 学校名・クラスは準個人情報に近く、子どもの所属が特定され得る。RLSの設計とプライバシーポリシー改訂を実装と同時に進めること。招待リンクの有効期限・再発行・脱退フローを最初から入れる。

---

### B-2. 通学路の家族共有（保護者2人目・祖父母） 🟡

**確認箇所**: `lib/database.types.ts:1612-1633` — `user_routes` は `user_id` の単一所有で、子どもは `child_name`（text）/ `child_id`（text）で保持。ルートを複数ユーザーで共有する仕組みが無い。

**問題**: **父と母が同じ子の同じ通学路を共有できない。** 片方が登録したルートをもう一方は見られないため、世帯の2人目・3人目（祖父母含む）がアプリに入る理由が構造的に弱い。1世帯1ユーザーで頭打ちになる。

**改善案**: ルートの共有オーナーシップ、または世帯（family）エンティティの導入。`docs/新機能追加.md`（親子ARモード仕様 v2.0）でも `children` テーブルの正規化が v2 スコープとして挙げられており、そこで一緒に設計するのが自然。

---

### B-3. オフライン耐性 🟡

**確認箇所**: `navigator.onLine` / offline を参照しているのは `components/providers/layout-provider.tsx`、`components/providers/supabase-provider.tsx`、`components/safety-quest/hunter/mask-confirm.tsx` の3ファイルのみ。**地図と危険箇所レポート投稿は未対応**。

**問題**: このアプリは「実際に通学路を歩きながら使う」ことを想定している（親子ARモード、きけんハンター）。電波の弱い場所・地下道・山間部で地図が落ちる、投稿が消える、という体験は現場利用の信頼を直接損なう。

**改善案**: 登録ルート周辺の地図タイル事前キャッシュ、投稿の下書きローカル保存＋復帰時の後送信。A-2 のPWA化と同じ Service Worker 基盤の上に乗るので、A-2 の後にやると効率が良い。

## C. 推奨実装順

| 順 | 施策 | 章 | 工数感 | 主に効く指標 |
|---|---|---|---|---|
| 1 | PWAマニフェスト追加＋ホーム画面追加導線＋**実機通知検証** | A-2 | 小 | iOS通知の解禁、再訪率 |
| 2 | 地図の公開ビュー（ログイン前に価値を見せる） | A-1 | 中 | 訪問→登録CVR |
| 3 | AI一次審査による自動承認（設計書あり） | A-3 | 中 | 投稿数、運用スループット |
| 4 | 鮮度確認UI（まだある/直りました） | A-5 | 小 | 情報信頼度、非投稿者の参加 |
| 5 | ふりがなの本体展開 | A-4 | 小〜中 | 子どもの利用時間 |
| 6 | 学校グループ＋招待リンク | B-1 | 大 | バイラル係数 |
| 7 | 通学路の家族共有 | B-2 | 中〜大 | 1世帯あたりユーザー数 |
| 8 | オフライン耐性 | B-3 | 中 | 現場利用の信頼性 |

1〜3 は「すでに作ってある資産が届いていないのを開通させる」性質の作業で、投資対効果が突出している。特に **1 は Push 通知一式を実装した後に抜けている**ため、現時点で最ももったいない箇所。

## D. この分析の限界（次に確認すべきこと）

本分析はコードとマイグレーションの静的な読み取りのみに基づく。以下は**未検証**であり、着手前に確認すること:

- iOS/Android 実機で Web Push が実際に届いているか（A-2 の前提）
- 現在の承認待ち件数と平均承認リードタイム（A-3 の深刻度）
- 実際の登録数・アクティブ率・投稿数の推移（優先順位の裏付け）
- `danger_reports` の最終更新日分布（A-5 の鮮度劣化がどれだけ進んでいるか。`docs/DANGER_REPORT_LIST_ANALYSIS_2026-07-07.md` では2026-07-07時点で公開18件中14件が90日以上前だった）
- 離脱がどこで起きているか（A-1 の仮説の裏付け。アナリティクスの導入状況は `lib/analytics.ts` を要確認）

数字が取れれば C の順序は入れ替わり得る。特に A-1 と A-3 の優先度は実データ次第。
