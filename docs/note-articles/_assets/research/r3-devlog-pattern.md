# R3: 個人開発記事がnote/Zennでバズる「型」調査

調査日: 2026-07-12 / 調査手段: Web検索(日本語)+主要記事の精読
対象プロダクト: PathGuardian(警察庁事故データ153万件を地図化・AIで写真から危険検出・子ども向けUI通学路安全アプリ / 個人開発)

---

## 0. 前提: note と Zenn の使い分け(調査結果の要約)

| 観点 | Zenn / Qiita | note |
|---|---|---|
| 読者 | エンジニア | 一般層(親・非エンジニア含む) |
| 向く内容 | 技術の深掘り・実装解説・ハマりどころ | **動機・葛藤・成長などのストーリー**、プロダクトの背景 |
| 拡散経路 | トレンド面・はてブ | **X(Twitter)拡散 + note編集部のおすすめ掲載** |
| 収益化 | 本販売・バッジ | 有料記事・メンバーシップ |

- 複数の比較記事([Zenn比較記事](https://zenn.dev/soshi1234/articles/note-qiita-zenn-comparison)、[Qiita活用術](https://qiita.com/ni4ta9/items/bbfc8b18c963bf148f39)、[noteの使い分け記事](https://note.com/finish/n/n0b12e8c6c2ce))が一致して指摘するのは「**技術解説はZenn、ストーリーはnote**」。
- noteでバズる4経路([noteでバズるパターン集](https://note.com/kawatyanlife/n/n11562a478ec1)): (1)著名人 (2)**note編集部おすすめ掲載(無名でも平等にチャンスあり)** (3)**X経由の拡散** (4)スキ返し(見かけだけ・非推奨)。無名の個人開発者が狙えるのは(2)(3)。
- PathGuardianの示唆: **親に届けたい話(子どもの安全・開発動機)はnote、技術詳細(Mapbox/153万件データ処理/AI判定)はZenn**に分け、相互リンクさせる二毛作が最適。

### 読まれる開発記事の共通構成(ストーリーアーク)

バズった記事はほぼ例外なく「**動機(個人的な原体験)→着手→挫折・失敗→転機→結果(数字)→学びの一般化**」の順。トレンド入りの秘訣を分析した[記事200本投稿の知見](https://zenn.dev/collabostyle/articles/858875b235cdd6)では、(1)タイトルに命をかける(数字・ターゲット明示・疑問形) (2)一次情報=自分の体験 (3)図解・スクショ (4)人の集まる場で公開、の4点が挙げられている。

### 数字・スクショ・失敗談の効かせ方

- **数字はタイトルに前置き**:「3週間で10万円」「10分で」「153万件」— 具体数値が信頼とクリック率を作る。盛らない実数がむしろ強い(小さい数字の正直さも共感を呼ぶ)。
- **スクショは Before/After と「動いた瞬間」**: 地図のヒートマップ、AI判定結果、子どもが使っている手元写真(顔なし)など、1スクロールに1画像が目安。
- **失敗談は「金額・時間」で定量化する**:「100万円かけて失敗」「240時間のコードを全削除」のように損失を数字で言うと拡散する。失敗→原因分析→回避策の3点セットで書く。

## 勝ちパターン14

### 型1. 「〜を作った/作ってみた」宣言型(王道)

- **説明**: 完成物を主語にした最短の型。何を・誰のために作ったかをタイトルだけで伝える。noteでもZennでも通用する基本形。
- **実例**: [幼稚園児にお金の価値を教えたくて「おこづかいアプリ」を作ってみた](https://note.com/jaga_farm/n/n7e070785c9cc) / [AIエージェントがすごいらしいので、検証がてらアプリを作った備忘録](https://zenn.dev/manycicadas/articles/4b1421d3b19e23)
- **PathGuardian適用**: 「小1の子どもの通学路が心配で、警察庁の事故データ153万件を地図にするアプリを作った」

### 型2. 数字ドリブン実績公開型(「全部公開する」)

- **説明**: 成果(収益・DL数・期間)を具体数値でタイトルに置き、やったこと全部を隠さず開示する。信頼性と再現性期待で拡散。
- **実例**: [開設後3週間で収益10万円を得た個人開発サイトでやったことの全部を公開する](https://qiita.com/jabba/items/1a49e860a09a613b09d4) / [個人開発アプリで10万DL達成するまでの試行錯誤をまとめてみた](https://qiita.com/maKunugi/items/86afc7e12fc96c709c84)
- **PathGuardian適用**: 「警察庁オープンデータ153万件を個人開発で地図化するまでにやったこと全部(前処理・コスト・ハマりどころ)を公開する」

### 型3. 失敗談全開示型(損失を数字で)

- **説明**: 失敗を金額・時間で定量化して晒す。成功談より共感・ブクマされやすい。「失敗8つと成功3つ」のように失敗を多めに並べるのがコツ。
- **実例**: [【個人開発】100万円かけて作ったサービスが失敗した話](https://qiita.com/Sicut_study/items/fee03dd7e20741a33bc5) / [5年間で作った個人開発・サービスの失敗例8つと成功例3つ](https://zenn.dev/s6lv/articles/0c628f662a4457)
- **PathGuardian適用**: 「153万件の事故データを地図に置いたらブラウザが死んだ話 — 個人開発で大規模データ可視化に失敗した3つのやり方」

### 型4. 「〜して分かったこと」学び抽出型

- **説明**: 体験を学び(一般化された教訓)に変換して差し出す。読者は「自分に転用できる知見」を求めてブクマする。
- **実例**: [個人開発で4つのプロダクトを作って分かった「企画倒れしない」アイデアの見つけ方](https://note.com/daijyu_dev/n/n1460efda4447) / [個人開発アプリを有料プレスリリース(3万円)で宣伝してわかったこと](https://note.com/studynow/n/n61a81a179ffb)
- **PathGuardian適用**: 「子ども向けアプリを個人開発して分かった、『大人向けUIの縮小版』が全く通用しない理由」

### 型5. 動機ストーリー型(「なぜ作ったか」= 原体験)

- **説明**: 技術より先に「作らざるを得なかった個人的な事情」を語る。note編集部おすすめに最も乗りやすい型で、非エンジニア読者に届く。
- **実例**: [私、子育て中のエンジニアが泣き声記録アプリを作ったワケ](https://note.com/kotoapp/n/n363bfa71d2ce) / [育児中、「こんなアプリあったらいいのに」と思ったら、自分で作ってた](https://note.com/rumiy826/n/nd75ffaa3af72)
- **PathGuardian適用**: 「子どもの通学路にある『あの交差点』が怖かった。だから警察庁のデータで確かめられるアプリを自分で作った」

### 型6. スピード驚き型(AI開発時代の新王道)

- **説明**: 「え、10分?」のような驚きの短時間+AIツール名(Claude Code等)をタイトルに入れる。AI開発ブームで2025-2026年に急伸した型。
- **実例**: [「え、10分?」37歳パパがClaude Codeで子どもアプリを作ったら、あっという間に公開できた話](https://note.com/yusuke_dev/n/n1dfa9d3110f6)
- **PathGuardian適用**: 「Claude Codeと二人三脚で通学路安全アプリを作ったら、レビュー・テスト・デザインまでAIと回す開発になった話」

### 型7. 属性ギャップ型(未経験/年齢/職業×成果)

- **説明**: 「未経験から」「37歳パパが」「19歳が」など、意外性のある属性を成果に掛け合わせる。読者の「自分にもできるかも」を刺激。
- **実例**: [AI絵本アプリを未経験から1人で作ってストア公開した話](https://qiita.com/h-uchiba/items/1c14e60e911b95caaa38) / 上記の「37歳パパ」記事
- **PathGuardian適用**: 「小学生の父親が、仕事の合間の個人開発で警察庁データ153万件のアプリを作って公開するまで」

### 型8. マイルストーン到達記型(心境の変化込み)

- **説明**: ユーザー数・DL数の節目に、数字だけでなく「心境の変化」を添えて書く。連続して書けるので育てやすい(1000人→1万人→10万人)。
- **実例**: [個人開発したアプリのユーザー数が1万人を超えて起きた心境の変化の話](https://note.com/hirothings/n/n86cb60f5ef38) / [個人開発サービスが「10万ダウンロード」されるまで](https://logmi.jp/main/technology/330748)
- **PathGuardian適用**: 「通学路安全アプリの利用者が最初の100家族を超えて、個人開発の『責任』が変わった話」

### 型9. 「やってよかった/やらなくてよかった/やっておけばよかった」棚卸し型

- **説明**: 施策を3分類で棚卸しする。網羅性とリスト性でブクマ需要が高い。振り返り記事の最強フォーマット。
- **実例**: [新規ユーザー獲得施策でやってよかったこと・やらなくてよかったこと・やっておけばよかったこと](https://logmi.jp/main/technology/330748)
- **PathGuardian適用**: 「子ども向け安全アプリのリリースでやってよかったこと・やらなくてよかったこと・やっておけばよかったこと」

### 型10. Build in Public 連載型(開発日記)

- **説明**: 開発途中から進捗・失敗・数字を継続発信する。日本では[リリース前発信でユーザー獲得2.4倍というデータ](https://shiftb.dev/articles/indie-dev-marketing)がある一方、[アイデア模倣リスク等のデメリット指摘](https://note.com/nosuke0926/n/nb80a7e6a6e73)もあり、模倣困難な資産(独自データ・コミュニティ)がある場合に向く。
- **実例**: [Build in Public という開発スタイル](https://note.com/kenzoarai/n/ncbb3210e65c3) / [界隈SNS開発日記 #2日目](https://zenn.dev/nakamasa/articles/55cecae351dbd6)
- **PathGuardian適用**: PathGuardianは「153万件データ+安全という公益テーマ」で模倣されにくく、Build in Public向き。「通学路安全アプリ開発日記」として機能追加ごとにnote連載+X進捗ポスト。

### 型11. 感情タイトル・心の声型(カギカッコ導入)

- **説明**: タイトル冒頭に「」で心の声・セリフを置く。「こんなはずじゃなかった」「え、10分?」など。感情が先に伝わりクリックされる。
- **実例**: [「こんなはずじゃなかった」どこで間違えた俺の個人開発](https://zenn.dev/furuchan/articles/8b891495c296e8)
- **PathGuardian適用**: 「『この道、通っちゃダメ』とデータが言っていた — 事故データ153万件を地図にして分かった通学路の盲点」

### 型12. 諦め・撤退・後悔型(ネガティブ告白)

- **説明**: 諦めた・後悔した・やりすぎた、というネガティブな告白は誠実さとして受け取られ、noteで特に読まれる。防御的でなく淡々と書くのがコツ。
- **実例**: [個人開発だけで食べていくのを諦めた話](https://note.com/08_14/n/nffdebdf95423) / [【個人開発】最初から作り込みすぎて後悔した話](https://note.com/bubecode/n/n5a6a40efe5e0)
- **PathGuardian適用**: 「機能を作り込みすぎて子どもに使われなかった話 — 通学路アプリで『引き算』を学んだ」

### 型13. 公共データ×可視化の社会性型

- **説明**: オープンデータを可視化して「社会が見える」記事は、技術者以外(行政・メディア・保護者)にも波及して拡散する。地図・ヒートマップのスクショ1枚が拡散の起点になる。
- **実例**: [交通事故オープンデータを色々分析してみる(ヒートマップ可視化編)](https://qiita.com/bb258/items/5f0c22d106de6030e79b) / [警察庁オープンデータの前処理と死亡事故発生予測](https://kamonohashiperry.com/archives/4424) / 警察庁自身も[オープンデータを公開](https://www.npa.go.jp/publications/statistics/koutsuu/opendata/index_opendata.html)しており題材の公共性が担保されている
- **PathGuardian適用**: 「警察庁の交通事故オープンデータ153万件、あなたの街はどう見えるか — 全国地図にして分かったこと」(自治体名・通学路名で刺さるスクショを複数枚)

### 型14. 掛け算ジャンル型(子育て×テック)

- **説明**: 「親としての課題×エンジニアスキル」の掛け算は、技術コミュニティと子育てコミュニティの両方に届く二重拡散ジャンル。ナキメモ・おこづかいアプリ・AI絵本など事例が厚く、noteと相性が最も良い。
- **実例**: [ナキメモ(泣き声記録アプリ)開発のワケ](https://note.com/kotoapp/n/n363bfa71d2ce) / [子育てエンジニアに聞いた育児で役立つITツール(Qiita Zine)](https://qiita.com/official-columns/interview/useful-tools-and-apps-for-childcare/) / [フルスタックお父さん(エンジニアHub)](https://eh-career.com/engineerhub/entry/2018/05/15/110000)
- **PathGuardian適用**: PathGuardianはこのジャンルのド真ん中。「エンジニア父親が子どもの通学路のために本気を出した」軸で、noteは親目線・Zennは実装目線で書き分ける。

## PathGuardian向け・記事化ロードマップ(提案)

1. **note第1弾(型5×型14)**: 動機ストーリー「子どもの通学路が怖くて、警察庁データ153万件のアプリを作った」→ 編集部おすすめ+X拡散狙い
2. **Zenn第1弾(型2×型13)**: 技術全公開「153万件の事故データをMapboxで軽快に描画するまでの全て」→ はてブ・トレンド狙い
3. **note第2弾(型3 or 12)**: 失敗談「作り込みすぎ/データ量で死んだ話」
4. **継続(型10×型8)**: Build in Public連載+マイルストーン記事(100家族→1000家族)
5. **各記事共通**: タイトルに実数、1スクロール1スクショ(地図ヒートマップ/AI判定/子どもの手元)、構成は「動機→挫折→転機→結果→学び」
