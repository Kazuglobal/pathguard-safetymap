「データを地図に重ねれば、通学路の危険が見えるはず」。そう思って警察庁の交通事故オープンデータ約153万件を地図に載せたら、ブラウザごと固まりました。これは、通学路の安全アプリを個人開発する私が、大規模データの可視化で盛大に転んでから、軽快に動くようになるまでの失敗の記録です。同じ道を通る誰かの回り道が、少しでも短くなれば。

## なぜ153万件を地図に載せたかったのか

私は「PathGuardian(パスガーディアン)」という、通学路の危険を見える化する家族向けのWebアプリを個人開発しています。技術スタックはNext.js(App Router)+ React + Mapbox GL + Supabaseです。

このアプリの柱のひとつが「事故ヒートマップ」。警察庁が公開している交通事故オープンデータ約153万件(2019〜2023年)を地図に重ねて、子どもが関わった事故・歩行者が関わった事故を絞り込んで見られるようにする機能です。

普通の地図には「ここで事故が多い」という情報は載っていません。でも公開データにはそれがある。だったら重ねて見せればいい——最初の発想は、それだけの素朴なものでした。

## 素朴な実装で、地図は静かに固まった

最初の実装は本当に素直でした。事故データを読み込んで、1件を1つのポイントとして地図に置く。開発中に一部の地域だけで試していたときは、何の問題もなく動いていました。

全国分のデータを流し込んだ瞬間、世界が変わりました。

(スクショ①: 改善前。ポイントの海に埋もれて操作を受け付けなくなった地図)

タブが応答しなくなり、地図はズームもスクロールもできない。開発者ツールを開くと、メモリ使用量がじわじわ育っていくのが見えます。描画が終わるのを待っても、今度はちょっと地図を動かすたびに画面が止まる。何かがクラッシュして親切なエラーを出してくれるわけでもなく、ただ「固まる」。これが一番つらいパターンです。

冷静に考えれば当たり前でした。153万件のポイントを全部ブラウザに送り、全部にレンダリングの面倒を見させる。1件あたりの処理はどんなに軽くても、153万倍すれば重い。データ量そのものが敵になる規模では、「動くコード」と「使えるコード」の間に深い谷があります。

## 試して、駄目だったアプローチたち

ここから回り道が始まります。駄目だった順に並べます。

**その1: 間引く。** 一定間隔でデータをサンプリングして表示件数を減らす。地図は動くようになりましたが、これは即却下でした。間引かれて消えた1件が、まさに子どもの通学路の交差点かもしれない。安全のためのアプリで「たまたま表示されなかった危険」を作るのは本末転倒です。

**その2: クライアント側でクラスタリングする。** 近い点をまとめて表示する定番の手法です。描画はましになりましたが、根本の問題が残りました。そもそも153万件ぶんのデータをブラウザに送ってパースする、その入り口が重いのです。表示を軽くしても、初回ロードの遅さと端末への負荷は消えません。親御さんが使うのは開発機ではなく、年季の入ったスマホかもしれないのに。

**その3: 表示中の範囲だけ都度取得する。** ズームインしている間は快適。でもズームアウトして市全体・県全体を見ようとした瞬間、結局大量のデータを要求してしまい、振り出しに戻ります。地図アプリは「引いて全体を見る」操作が必ず起きるので、ここから逃げられません。

3つに共通する敗因はひとつでした。**「持っているデータ」と「画面に表示する情報」を同じものだと思い込んでいた**ことです。

## 転機:「全部の点を送る」のをやめる

発想を変えました。ズームアウトした地図を見ている人が知りたいのは、153万個の点の正確な位置ではなく「どのあたりに事故が集中しているか」という傾向です。それなら、点を送る必要はない。**あらかじめ空間的に集計した結果だけを送ればいい。**

具体的には、事前処理でデータを地理的なまとまりごとに集計しておき、ズームレベルに応じて渡す粒度を変えます。引いて見ているときは集計値をヒートマップとして面で見せる。ズームインするほど細かい情報に切り替える。地点ごとには事故リスクのスコアを算出して、「この場所はどうか」に答えられるようにする。

(スクショ②: 改善後。ヒートマップで事故の集中が面として見え、操作も軽快な地図)

ブラウザに届くデータは「その画面を描くのに必要な量」だけになり、地図はスマホでもすっと動くようになりました。153万件という数字は変わっていないのに、体感はまるで別のアプリです。固まる地図を前に頭を抱えていた日々を思うと、直した内容より「どこを直すべきだったか」に気づくまでが長かった、というのが正直なところです。

## 個人開発で性能問題とどう向き合うか

この経験から持ち帰った教訓を、一般化して置いておきます。

**データ量は「仕様」である。** 153万件を扱うと決めた時点で、性能設計は後回しにできないオプションではなく要件でした。早すぎる最適化は悪と言われますが、データ規模が最初から分かっているなら、それは「早すぎ」ではありません。

**表示する情報と保持するデータを分ける。** ユーザーが見たいのは点の集合ではなく意味です。「何を見せたいか」から逆算すると、送るべきデータは劇的に減ります。

**一番弱い端末を基準にする。** 開発機で動くことには何の意味もありませんでした。使ってほしい相手の手の中にあるのは、数年前のスマホかもしれません。

**固まってから直すのではなく、固まった理由を言葉にする。** 「重い」で止めずに、入り口(転送・パース)なのか描画なのか操作時なのかを切り分ける。私の場合、3つの失敗はどれも切り分けの解像度が足りないまま対症療法に走った結果でした。

---

まとめます。153万件をそのまま地図に置いて固まり、間引き・クラスタリング・範囲取得で回り道をして、「集計結果だけを送る」ことでようやく軽快になりました。失敗の核心は技術ではなく、「持っているデータを全部見せようとした」設計の思い込みでした。

もしお子さんがいる方なら、お住まいの地域の事故データや自治体の公開情報を、一度親子で眺めてみてください。「この道、車が多いね」という何気ない会話が、通学路を見る目を変えてくれます。
